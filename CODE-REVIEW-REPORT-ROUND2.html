发现问题

JWT_SECRET 在三处独立定义（auth.module.ts / auth.service.ts / jwt.strategy.ts）
每个文件都有 const JWT_SECRET = process.env.JWT_SECRET || '...'，重复且不一致风险增加。建议提取到 config/auth.config.ts 统一管理。
auth.service.ts 中 jwtService.sign() 冗余传递 secret
JwtModule.register() 已配置 secret，sign() 无需再次传入。当前传入的参数与模块配置相同所以功能正确，但冗余代码增加维护成本。建议改为 this.jwtService.sign(payload)。
AuthService 硬编码默认密码 contentops2024
可通过 AUTH_PASSWORD 环境变量覆盖。本地工具场景可接受，但建议在 README 中注明修改默认密码。

正向验证 ✅

  • 登录页为 @Public() + POST /api/auth/login，匿名可访问
  • Health 端点为 @Public()，监控无需认证
  • 全局 JwtAuthGuard 保护所有其他端点
  • Guard 通过 Reflector 读取 @Public() 元数据，逻辑正确
  • Passport JWT Strategy 从 Authorization: Bearer xxx 提取 token
  • Token 24h 过期，无 refresh 机制（本地工具可接受）

3. 集成点审查（app.module.ts + main.ts）

Guard 注册顺序

APP_GUARD: JwtAuthGuard    ← 先执行：验证 token
APP_GUARD: ThrottlerGuard  ← 后执行：计数

顺序正确。登录端点 @Public() 让 JwtAuthGuard 跳过，ThrottlerGuard 正常生效，登录接口受速率保护。保护端点 token 先校验再入限流桶。

main.ts 中间件链

compression → securityHeaders → CORS → ValidationPipe → static files → *splat fallback

中间件顺序正确。securityHeaders 在 CORS 之前确保安全头无条件附加。*splat 路由将 /api 和 /health 排除，不拦截 API 流量。

未认证请求不会消耗 ThrottlerLimit
JwtAuthGuard 抛出时 ThrottlerGuard 还未执行，无效 token 不计入速率限制。对于防御暴力破解，应在 ThrottlerGuard 之前做计数。建议调整顺序：@SkipThrottle 不使用，改为在登录端点加 @Throttle() 单独控制。当前风险低，可后续优化。

发现问题

LoginView 未使用 redirect 查询参数
router guard 将 to.fullPath 传入 query: { redirect: ... }，但 LoginView 登录成功后固定跳转 router.push('/')。用户登录后不会回到原本想访问的页面。建议读取 route.query.redirect 并跳转。
过期 token 会短暂进入页面再被踢出
路由守卫仅检查 localStorage 中有无 token（不检验 expiry），过期 token 会先放行，等首次 API 调用返回 401 才重定向到登录页。用户会看到页面内容一闪而过。改进方案：可在 auth store 中解析 JWT exp 字段做本地过期判断。
并发 API 调用 401 时 clearAuth() 和 redirect 重复执行
若多个 API 同时返回 401，每个拦截器都会调用 clearAuth() 和 window.location.hash 赋值。功能上无害（幂等操作），但理论上哈希可能被反复设置。可加一个标志位防抖，优先级低。

正向验证 ✅

  • LoginView 使用独立 axios 实例（非 http-client），不携带 auth header，不会触发拦截器循环
  • Vue 模板渲染中 user-provided 错误信息经 Vue 自动 HTML 转义，无 XSS 风险
  • window.location.hash = '#/login' 使用 hash 路由兼容 createWebHistory
  • auth store 的 getAuthHeader() 方法已定义但未使用（http-client 直接读 store.token），保留了扩展性

$executeRawUnsafe 复查

全量 6 处用法均已核查：

  • DDL（CREATE TABLE / ALTER TABLE / CREATE INDEX）：无用户输入，安全 ✅
  • DML（INSERT ... VALUES (?...?) ON CONFLICT）：参数绑定 + 分批 50 行，安全 ✅
  • SELECT ... IN (?...?)：参数绑定，安全 ✅
  • ALERT_UPSERT_SQL：参数绑定，安全 ✅

结论：所有 $executeRawUnsafe 用法均通过参数绑定或静态 DDL，不存在 SQL 注入风险。原报告标记为潜在风险，二审确认安全。
